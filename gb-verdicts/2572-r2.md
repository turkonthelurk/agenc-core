# 2572 r2 verdict

**Blocking.** One rollout ordering still admits two live owners and can report success after both plugin versions are gone.

Reviewed `b9795f5d199cdcec49a5d3f26a8a6564d0e5ff9f..087bdc8ae34f54b267a91db8da9f083f043ea541` (6 files, +524 / −142). Same-build participants that use this tree no longer have an ordering I can construct where two of them delete the wrong plugin tree, both enter one critical section, or return success for a tree the other already removed. The blocking case is an old lock holder (`b9795f5`) overlapping a new one (`087bdc8`) on a directory whose final component is not already NFC-lowercase.

## Finding

[P0] Case-folding the lock key splits exclusion with the previous lock build

File: `runtime/src/plugins/cli/plugin-install-directory-lock.ts:712`

`b9795f5` keyed an existing directory by `realpath(destination)`, byte for byte. This diff keys by the real parent plus `basename.normalize("NFC").toLowerCase()` (`plugin-install-directory-lock.ts:712-720`). The lock file name is the SHA-256 of that whole string (`lockFilePath`). `pluginFilesystemKey` keeps the plugin id's letters (`runtime/src/plugins/directories.ts:101-109`), so an id such as `PDF` is installed as:

`PDF--1d393b0081b632c54654eb08c345ff76b92ae4efe0768b4c0f64b9ebbe920492`

Those two formulas do not name the same lock:

| Build     | Key basename         | Lock file under `{storage}/.plugin-install-ops/`                                    |
| --------- | -------------------- | ----------------------------------------------------------------------------------- |
| `b9795f5` | `PDF--1d393b00…0492` | `install-dir-2db5e9e782cb14fd5c73e2227b39bcdb06d674588bc014b62dbb41bf1041e7ec.lock` |
| `087bdc8` | `pdf--1d393b00…0492` | `install-dir-1353d43d8e4db08548d0a8b32d5c0a2f7630b81856e5c171711c7a26a3214563.lock` |

`{storage}` is the real path of the plugin root. Both files sit in the same ops directory. `link` of one does not conflict with the other.

Actors: `P_old` is `updatePluginOp` on `b9795f5`. `P_new` is `uninstallPluginOp` on `087bdc8`. Same host, same pid namespace, both alive. Plugin id `PDF`. No non-participant.

Initial state: `{storage}/PDF--1d393b00…0492` is v1. User config has `PDF` enabled. No lock files.

1. `P_old` links the `2db5…` lock and enters the transaction. It renames the directory to `PDF--1d393b00…0492.bak-{op}`, then renames its stage onto the destination. State: destination is v2, backup is v1, config still enabled. `P_old` has not published config or written `committed`.
2. `P_new` resolves that same directory and lowercases the key. It links the `1353…` lock while `P_old` still holds `2db5…`. It does not wait.
3. `P_new` `rm`s `{storage}/PDF--1d393b00…0492` (`pluginOperations.ts:754`). v2 is gone. `pluginIdRemainsInstalled` is false, so it deletes the `PDF` config entry and returns success with `removedConfig: true`. Backup v1 is still there.
4. `P_old` publishes `{ enabled: true }`, writes `committed`, then `removeMatchingDirectory` deletes the v1 backup because that identity still matches. `P_old` returns success.

Observed: both commands returned success. v2 was removed in step 3. v1 was removed in step 4. Config is enabled because step 4 wrote it after step 3. The next load has an enabled id and no directory. Nothing on disk can restore either version. Swapping the config writes leaves config absent instead; the update has still returned success for a tree that was already deleted.

The same split is two first installs of `PDF` before the directory exists. Each `link` succeeds. Both `rename` a stage onto `{storage}/PDF--1d393b00…0492` and both write the config entry. One success is the other's tree.

This is not the accepted mixed-build reclaim race. No guard is dead, nobody unlinks a path after a stale read, and both holders are live for the whole overlap. It is also not "case-folding serializes legacy case-only pairs." That residual is same-build: `087bdc8` against `087bdc8` folds `PDF--…` and `pdf--…` onto one key and runs them one at a time. Here the old process never folds, so the critical sections overlap.

A lowercase final component that is not a symlink still matches across these two builds: `realpath(dir)` equals real-parent plus that basename, and both hash the same string. `demo` is fine. Any id with an uppercase letter is not, because the readable prefix keeps that case.

Secondary ordering from the same formula, narrower than the uppercase one: if the string passed into the lock has a symlink as its final component, `b9795f5` follows it and `087bdc8` does not (`plugin-install-directory-lock.ts:42-46`, `712-715`). Two locks, one path, same overlap as above. Normal `installPluginOp` does not do this for an existing directory: `existingRoots[0]` is already a `realpath`, so both builds lock the target. It shows up when the locked string itself is the symlink.

Same-build reclaim does not have this hole. A dead guard or dead lock is removed only while holding `lock.reclaim-<nonce>`, and `claimAndRemove` unlinks the private claim name only after the open file's bytes and dev/ino match the judged file (`plugin-install-directory-lock.ts:508-578`). A second new-build reclaimer cannot enter that section while the first holder's pid is live in this namespace. I could not construct a participant-only interleaving that unlinks the other process's lock or admits two new-build holders.

Fix: while `b9795f5` can still be running, also acquire the legacy key (`realpath` when the last component exists, otherwise real parent plus the original basename) and hold it across the same section as the folded key. Order the pair the same way in every process. After no `b9795f5` process remains, the legacy key can go.

## Accepted residuals

Not blocking, and not widened by this diff:

- Mixed old/new reclaim. An old process can still unlink whatever is at the lock or guard path after its stale read. `claimAndRemove` treating `ENOENT` as "removed" does not add a second way for two `087bdc8` processes to both enter. It only lets the new process proceed after the old process has already stolen the name, which is the accepted race.
- Cross-scope uninstall versus install. Uninstall now holds the same-scope roots and the default root through config, data, and catalog cleanup (`pluginOperations.ts:742-746`). It still does not lock the other scope. The cross-scope window is the same length as before.
- Pid reuse, other pid namespaces, same-async-context re-entry, non-participants, and case-folding that serializes two legacy spellings under `087bdc8` only. Unchanged in kind.
- A reclaim-key chain deeper than `MAX_RECLAIM_KEY_DEPTH` (4) makes a new process return busy instead of taking the lock (`plugin-install-directory-lock.ts:530-533`). That refuses a second owner. It does not delete a live file. It can stall reclaim until those key files are removed by hand.
